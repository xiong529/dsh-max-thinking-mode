# `isolated_review` 工具指南

`isolated_review` 是最大思考模式最具标志性的工具。它把方案交给一个或多个**隔离评审者**——没有工具、没有文件、没有网络、没有对话历史的全新子 agent——并返回它们的结构化裁决。

本指南说明：每个参数的含义、三种审思形态、如何写好评审问题、以及成本影响。

---

## 1. 隔离意味着什么

该工具派生出的评审者被**双重隔离**：

1. **全新上下文**：子 agent 提供方（如 `spawn`）隐藏父对话与所有已完成轮次。评审者从未见过你的推理过程。
2. **无工具**：`toolFilter` 不保留任何继承工具，加上固定评审者 persona——评审者手里只有你传入的上下文。它不能读文件、跑命令、联网、委派，也不能问用户。

所以评审者**只依据你的框架作答**。这正是要点：你得到的意见真正独立于你自己的推理——但它的质量完全取决于你提供的上下文。

---

## 2. 参数

| 参数 | 必填 | 含义 |
|---|---|---|
| `task_context` | 是 | 评审者推理所需的一切：问题、约束、需求、证据。评审者没有工具，**上下文不完整就是静默失败**——该给的都要给，多余的不要给。 |
| `proposed_solution` | 是 | 你最终形成的方案或计划。评审者会独立重新思考这个问题并尝试反驳它。 |
| `alternative_angle` | 否 | 要求评审者采取的不同视角，如"从最小资源消耗的角度"或"从长期维护的角度"。省略则由评审者自选。 |
| `review_focus` | 否 | 需要重点审查的方面，如正确性、失败模式、可维护性、安全性。省略则整体审查。 |
| `review_question` | 否（但建议） | 你想让评审者回答的具体问题，按场景撰写。见 §4。 |
| `reviewers` | 否 | 并行评审者数量（1–3，默认 1）。每位独立重新思考，且必须贡献一个其他评审者想不到的观点。 |
| `prior_review` | 否 | 粘贴第一轮评审的结构化裁决，开启**第二轮对抗**。需配合 `submitter_rebuttal`。 |
| `submitter_rebuttal` | 否 | 你对第一轮评审的回应——你接受哪些反对意见、拒绝哪些、理由是什么。需配合 `prior_review`。 |
| `arbitrate` | 否 | 为 `true` 时，评审者返回后，一位同样隔离的终审仲裁者逐条采纳或驳回反对意见、防范群体思维，并给出所选方向的最强进化方向。 |

### 评审者输出（结构化裁决）

每位评审者恰好返回以下字段：

| 字段 | 含义 |
|---|---|
| `verdict` | `sound-as-is`（原样可用）/ `sound-with-changes`（需修改）/ `different-approach`（应换方案） |
| `objections` | 每条反对意见：一个缺乏支撑或有风险的点及其原因 |
| `strongest_weakness` | 最具破坏性的单一缺陷 |
| `verdict_reason` | 作出该裁决的推理 |

### 仲裁者输出（`arbitrate: true` 时）

| 字段 | 含义 |
|---|---|
| `final_verdict` | `sound-as-is` / `sound-with-changes` / `different-approach` |
| `decision` | 你应该采取的方向 |
| `accepted_objections` | 你必须回应的反对意见 |
| `rejected_objections` | 仲裁者驳回的反对意见及理由 |
| `evolution` | 能让所选方向变强的最优下一步（已经完善则为空） |

## 3. 三种审思形态

### 形态一 · 单次评审（默认）

```
task_context + proposed_solution（+ angle / focus / question）
        └─▶ 1..3 位隔离评审者 ──▶ 结构化裁决
```

适用：设计取舍、不熟悉的实现、方案对比。

### 形态二 · 第二轮对抗

```
第一轮裁决   （prior_review）
        +
你的反驳     （submitter_rebuttal）
        └─▶ 评审者诚实再评估：
             承认你已回答的，追问你回避的
             ──▶ 以相同结构化字段给出最终裁决
```

适用：第一轮裁决挑战了你的方案，你想回应而不是直接接受或忽略。

### 形态三 · 终审仲裁

```
评审者裁决（1..3 位）
        └─▶ 终审仲裁者（同样隔离）
             逐条采纳/驳回反对意见并说明理由
             防范群体思维
             ──▶ 最终裁决 + 进化方向
```

适用：重大决策的最终定夺——希望反对意见在动手前被逐条权衡。

---

## 4. 如何写好 `review_question`

问题由你撰写——按场景选择。persona 给出了这些映射：

| 场景 | 合适的问题 |
|---|---|
| 设计取舍 | "这个方案对给定约束是否是合适的适配与风险？" |
| 不熟悉的实现 | "什么会让它在生产中失败？" |
| 方案对比 | "哪一个能扛过最强的反对意见？" |
| 需求模糊 | "这个计划假设了什么？假设成立吗？" |

好问题要精确、且仅凭上下文就能回答。模糊的问题只会得到模糊的裁决。

---

## 5. 何时使用（以及何时不用）

**该用**：重大决策——改动成本高的设计、不熟悉的实现、难以逆转的选择、会带偏后续分支的模糊需求。

**不该用**：日常修复、琐碎选择、或任何"第二意见的价值 < 评审成本（全新子 agent + token）"的情形。

模式的 persona 只为重大决策调用 `isolated_review`；调用与否的决定权在模型，评审之后的最终决定权也在模型。

---

## 6. 成本与 token 行为

- 每次调用派生 1–3 个全新子 agent（`arbitrate` 时再加一个仲裁者），每个读取传入的上下文并产出一份回复。子 agent 的系统提示极简（身份 + 评审者 persona，无工具段落）。
- 成本随 `task_context` 长度与评审者回复长度增长。
- 子 agent 是全新会话，不复用父提示词前缀，所以**KV 缓存与父会话不共享**；父日志以普通事件记录该工具调用及其结果。
- 并行评审（2–3 位）并发运行——token 成本是所有评审者运行之和。

---

## 7. 局限（对自己诚实）

- **评审者无法验证任何东西。** 它只依据你传入的上下文推理。如果某个论断依赖仓库、代码或外部事实，请自己把证据传进去——并在行动前用真实世界核实评审者的反对意见。
- **框架是你的。** 评审者从你选择的角度和问题作答。有偏见或不完整的 `task_context` 会产生同方向的偏见评审。如果你怀疑自己的框架，就用 `alternative_angle` 要求一个刻意的不同视角。
- **每次调用是一次同步评审。** 暂不支持后台/可续接模式：你无法在同一次调用中通过后续问题引导评审者。第二轮对抗（`prior_review` + `submitter_rebuttal`）就是为此提供的迭代方式。
