# 在全新难题上评估 Agent 预设模式

[English](evaluating-agent-preset-modes.md) | 中文

## 何时使用

预设承载着一句承诺：面对没有现成答案的问题，最大思考模式比标准模式解得更好。在相信这句承诺、以及进一步调它的 persona 之前，先拿真实任务量一量。本页给出一个小而可复现的协议，评分对象是**方案的优劣与突破点的强度**，而不是代码正确率或测试通过率。

## 测量什么

每次运行在四个维度上打分，全部由人阅读最终答案后评判：

| 维度 | 衡量什么 | 量程 |
|---|---|---|
| 方案质量 | 最终方案是否真的解决了问题 | 1（没有）– 5（完全） |
| 突破强度 | 思路离第一直觉有多远；数出出现的独立突破点（重新定义问题、跨领域类比、反转约束等） | 0–n 个独立点 |
| 可行性 | 方案能否以合理工作量落地 | 1（不能）– 5（能） |
| 成本 | 工具调用次数与 token | 计数 / 计数 |

这些维度刻意排除代码正确率：下面五个任务里有两个是纯设计任务，一行代码都没有。你评判的是 Agent 给出的答案，而不是它的实现方式。

## 任务集

两种模式都跑同样的五个任务。每个都是生态内没有现成解法的问题，明显的路径往往是错的或未知的。

1. **设计访客预览功能** —— 一个 Web 应用要让未登录访客预览工作区文档，但不能有任何写权限，团队从未做过。约束：访客不能看到会泄露内部结构的文件路径或元数据。产出设计及其威胁模型。
2. **迁移手写的权限系统** —— 一个成熟代码库在各调用点散落临时角色检查，团队必须在不留迁移窗口的情况下替换它。没有现成工具能解决这个形态。产出迁移策略与目标模型。
3. **渲染带数学公式的 Markdown** —— 应用要在客户端离线渲染带 LaTeX 数学公式的 Markdown，且不能使用现有库，团队不知道哪条路可行。产出被证明可行的方案（附原型或证据）。
4. **突破性能瓶颈** —— 一个任务队列 60% 的时间花在争夺一把锁上；标准分片无效，因为热点键无法避免。产出不是常规分片思路的方案。
5. **从零发明全新功能** —— 产品需要一个别处没有的新协作功能，全部需求就是用户写的一段话。

## 协议

- 两种模式使用同一模型提供方与同一模型。
- 每次运行从相同的工作区状态开始（适用时用干净检出）。
- 给两种模式完全相同的任务文本。对最大思考模式，保持用户输入尽量少——该模式本应自主决定探索方向。
- 每个任务两种模式**各至少跑一次**；时间允许时各跑三次取中位数，因为单次运行会把模式质量与采样噪声混在一起。
- 每次运行记录：模式、任务、最终答案、四个维度得分、工具调用数、token 用量、墙钟时间。
- 同一任务的全部答案一起评判（有条件时对模式盲评，由第二人打分）。

## 运行方式

配置 API key（`DEEPSEEK_API_KEY`）后，在 Web GUI 新建任务并从模式菜单选择：对照组选标准模式，实验组选最大思考模式。粘贴任务文本，等运行结束再打分。要做批量时，用两个分别挂载 `standard` 与 `deep-think` 预设的组合驱动同一输入，并收集记录的会话日志（`request/header` 携带工具目录；会话统计报告 token 用量）。

## 怎么判读得分

- **最大思考在突破强度上胜出、可行性相当** —— 模式按设计工作；下一步优化成本。
- **突破强度没差别，工具调用也没变多** —— 外求探索与隔离审思策略没有改变行为；先排查 persona 再相信它。
- **成本暴涨但方案质量没提升** —— 深度思考机制在这里只是噪声；考虑收敛触发条件（仅重大决策）或限制 `reviewers`/轮数预算。
- **某个任务只有一种模式解出** —— 这个任务信息量最大；先重跑三次再下结论。

用类似下表记录结果，并随调整 persona 的改动一起保留：

| 任务 | 模式 | 方案 | 突破点 | 可行性 | 工具 | Tokens |
|---|---|---|---|---|---|---|
| 1 | 标准 | 3 | 1 | 4 | 12 | 18k |
| 1 | 最大思考 | 4 | 3 | 4 | 41 | 63k |
