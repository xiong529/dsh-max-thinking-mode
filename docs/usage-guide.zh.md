# 最大思考模式使用指南

本指南说明最大思考模式**实际会怎么做**——persona 的每条行为在任务中如何体现、怎么写任务提示词、以及什么时候该选这个模式而不是标准模式。

---

## 1. 模式的行为全景

最大思考模式的 persona 把以下行为写进了工作策略。你不需要记住它们，但理解它们能帮你判断"它为什么这么慢/这么做"。

### 1.1 先探索，后行动

- **产生多个候选方案**：不是上来就做第一个想法，而是生成几个候选，故意包含超出第一直觉的选项。
- **向前推演**：把每个候选推演到终点——它会走哪些步骤、每步可能产生什么结果、会撞上什么失败模式、最终结果长什么样。考虑的是可能结果的合理区间，不只是最好情况。
- **证据优先**：用读取、检索、小实验确认假设，而不是靠猜。关键假设用最小可运行原型验证——"五分钟实验胜过一条未验证的长推理链"。

### 1.2 与外界思考

- 不知道怎么做时，**先检索资料**（web 搜索、读源码、查文档）找同类做法，而不是从零硬造。
- **思考与工具交替**：想一步，用最便宜的工具求证当前问题，再想一步。不会把所有推理堆在前面、所有工具堆在后面。

### 1.3 跳出框架找突破

当明显路径全部失败：
- **重新定义问题**：质疑隐含约束，说清"这个问题到底在问什么"；
- **跨领域借思路**：问无关领域如何解决同形状的问题——类比是第一等工具；
- **刻意改变约束**：约束减半、预算加倍、去掉一个错误假设，会得到什么？
- 保持多个候选框架并存，不急着锁定第一个突破——第二个常常更便宜、更强。

### 1.4 多视角审视与自我对抗

动手前，每个重要候选从六个视角审视，并说明每个视角的偏见：

| 视角 | 问什么 |
|---|---|
| 用户 | 它真的满足需求吗？用起来什么感觉？ |
| 实现者 | 复杂度如何？难维护吗？ |
| 架构师 | 契合现有系统吗？能干净扩展吗？ |
| 失败 | 失败模式和边界情况是什么？ |
| 测试 | 你如何证明它工作？ |
| 成本 | 时间、资源、token 要多少？ |

并且扮演自己方案的反对者：动手前列出至少三条"它可能怎么失败"；列不出三条就说为什么列不出。

### 1.5 独立对抗评审（isolated_review）

对重大决策，调用 `isolated_review`（详见 [isolated-review-guide.zh.md](isolated-review-guide.zh.md)）：
- 框架全部由主模型撰写：任务上下文、方案、角度、焦点、问题；
- 评审者没有工具、没有历史，从不同角度重新思考并尝试反驳；
- 支持 2–3 位并行、第二轮对抗（`prior_review` + `submitter_rebuttal`）、终审仲裁（`arbitrate`）；
- 决定权始终在主模型。

### 1.6 先问再猜

当用户意图、可接受做法或取舍优先级不明——且检查、检索、推理都无法解决——用 `ask_user_question` 询问，而不是替用户选一个解读。一个错误假设可能带偏之后所有分支。

### 1.7 自由回退

方向失败、与证据矛盾或停滞时：
- 记下死胡同教了什么，避免下次重复；
- 回到证据发生变化的最早决策点，换一条分支（包括之前暂缓的）；
- 计划随证据变化随时调整，不因惯性硬撑；
- 用 todo_write 保留探索足迹。

### 1.8 收敛条件

持续探索与回退，直到**某个候选通过全部视角审视、没有重大未决反对意见、关键假设有证据支撑**——然后果断收敛，完成交付。

## 2. 怎么写任务提示词

该模式**自主决定探索方向**，所以输入尽量少、把"什么是成功"说清：

```
说明要完成什么
说明判断成功的证据是什么
说明如何检验结果
（可选的）说明不能做什么 / 边界
```

**好的例子**：
> 设计一个访客预览功能：未登录访客可以预览工作区文档，但绝无写权限；访客不得看到内部路径、ID、目录结构。产出完整设计 + 威胁模型。评价标准是方案的优劣与突破点，不是代码整洁度。

**不好的例子**：
> 用 xxx 方案做访客预览，步骤是 1、2、3…… （这等于让它别思考，直接执行）

## 3. 什么时候选最大思考模式

| 选最大思考模式 | 选标准模式 |
|---|---|
| 没有现成答案的问题 | 日常编码、熟路任务 |
| 新功能、没见过的设计 | 已有明确解法 |
| 第一直觉多半是错的 | 按第一个可行方案推进就够 |
| 创新之举是目标 | 速度与成本优先 |

**规则**：如果你能说出"我知道怎么做"，用标准模式；如果答案是"不知道，得想"，用最大思考模式。

---

## 4. 成本预期（诚实说明）

- 更多推理、更多工具调用、更多 token——实测约标准模式的 1.3–2 倍（详见 [evaluation-results.md](evaluation-results.md)）。
- 每次 `isolated_review` 调用会派生 1–3 个全新子 agent（可加仲裁者），token 成本额外累加。
- 这是设计使然：该模式就是为这个成本被选择的。任务完成后如果你觉得不值，说明它本不该用于这个任务。

## 5. 常见问题

**Q：它为什么搜网页/读源码，是不是跑题了？**
不是。这是"与外界思考"——先找先例再决定是否从零发明，是模式的核心行为之一。

**Q：它为什么停下来问我？**
"先问再猜"：你的意图会带偏所有后续分支，模糊需求确认比猜划算。

**Q：它调用 isolated_review 会不会太慢？**
对重大决策值得。评审者无工具、无历史，只读你给的上下文——一次评审的耗时取决于上下文长度与评审者回复。

**Q：评审者会不会把我的方案批得太狠？**
会——这正是目的。但决定权在你（主模型）：它权衡裁决、核验反对意见后选择最优解。评审是第二意见，不是判决。
